## 叙事结构

采用「三个反直觉的决定」结构：先用 800 字建立共鸣与全景，再以三个设计决策为主体各自独立成节，最后用真实踩坑收束。

选择理由：目的是"讲设计思路"，决策就应站在台前而非藏在数据流流水账里。每节自带钩子，读者中途放下也能读完一节有收获。对嵌入式读者，决定一与决定三有天然共鸣（Manifest、ADB 踩坑），决定二正好覆盖其知识盲区，集中一节讲透优于散落全文。

已否决的两个方案：
- **一条红线串全场**（从"最直觉的做法"逐步推倒，终点是三层架构）——论证张力最强但偏论文腔，中途放下即白读。
- **跟着一次 push 走完全程**（纯数据流叙事）——最具象，但决策点被数据流打散，方法论凝聚不起来，易滑成模块介绍流水账，与"讲设计思路"的目的冲突。

### 骨架层面的三个取舍

1. **开篇不提 AI/LLM。** 系统名含 "AI"，但若开篇即讲 LLM Agent，读者注意力会被"又一个 AI 项目"带走，而全文最硬的观点恰恰是把 LLM 挡在关键路径之外。LLM 第一次出现应在决定二，以"我们决定不让它做什么"的身份登场。
2. **全景图重画，不复用施工图。** `docs/device-test-sequence.md` 的时序图有 13 个参与者，是开发用施工图，放进博客会劝退。博客版画 5 个方框的横向流程图。
3. **三节顺序按认知负荷递增再回落**，而非按数据流：从读者最熟的打包讲起（决定一），中间啃概念（决定二），最后用 ADB 实战收尾（决定三），让人舒服地读完。

## 三个决策的论证线

### 决定一：设备上跑什么，打包那一刻就定死了

**钩子**：运行时才知道设备什么情况，为什么要在打包时把命令写死？

**论证链**：
1. 最直觉的做法有三种——Agent 侧放配置、调度端下发命令、让 LLM 临场生成 adb 命令。
2. 都不行，因为 8 个变体的执行方式在三个维度上全不相同（数据见下表），一旦执行方式存在 Agent 侧，Agent 升级一次就可能把某个变体测错，且错得静默。
3. 更要命的是不可审计：三个月后问"当时那次到底跑的什么命令"，答不出来。
4. 结论：`manifest.yaml` 打进包里，声明 requirements / deploy / test / collect / cleanup，Agent 严格照做。

**三个维度的真实差异**（取自 `ci/variants.yaml`，写作时以该文件为准）：

| 维度 | SNPE (Android) | RKNN (Android) | TFLite (Android) |
|---|---|---|---|
| env | 多一个 `ADSP_LIBRARY_PATH`，且含系统 DSP 路径 `/system/lib/rfsa/adsp` | 仅 `LD_LIBRARY_PATH` | 仅 `LD_LIBRARY_PATH` |
| 设备要求 | `soc: [QCM6125]` + `capabilities: [hexagon]` | `soc: [RK3588, RK3566]` + `capabilities: [rknpu]` | 无 soc / capabilities 要求，纯 CPU 亦可 |
| 失败签名 | `cpu_fallback`→MODEL；`dsp_unavailable`→DELEGATE | `rknn_init_fail`→DELEGATE | `delegate_fallback`→DELEGATE |

注意同一句 "Falling back to CPU"，在 SNPE 变体里叫 `cpu_fallback` 判 MODEL，在 TFLite 变体里叫 `delegate_fallback` 判 DELEGATE——同样的日志文本，归因不同。这是"执行方无法自行推断、必须由打包方声明"的最直接证据。

**落地细节（选三）**：
- Manifest 由 CI 按 `ci/variants.yaml` 渲染，8 个变体一张表，失败签名规则也在这张表里——同一张表同时喂给打包端与判定端。
- **签名扫描位置是实测出来的知识**：Android 变体扫 `stdout`，Linux 变体扫 `stderr`。`variants.yaml` 中留有注释说明缘由（2026-07-22 实测：SDK 测试二进制输出走 `stdout.log`，不进 logcat，扫 logcat 永远命中不到；native_crash 除外，系统 tombstone 确实在 logcat）。这类知识只能实机跑出来，也正因如此必须固化进契约，不能留给执行方去猜——本条同时为决定三埋下伏笔。
- 包内另有 `files.sha256` 逐文件校验。整包 sha256 只证明"下载没坏"，逐文件才证明"打包机注入的 manifest 与包内实际内容一致"。
- Agent 的 adb 层没有 `Exec(cmd string)`，只有一组返回参数数组的模板函数。

**收尾金句**：把"做什么"和"谁来做"分开——让"做什么"跟着产物走，而不是跟着执行者走。

**引用路径**：`ci/variants.yaml`、`ci/gen_manifest.py`、`agent/internal/manifest/manifest.go`、`agent/internal/adb/adb.go`

### 决定二：判成败的代码只有 89 行，且绝不问 LLM

**钩子**：都上 LLM 了，判个测试过没过这么简单的事，为什么专门写 89 行 if-else？

**数字的精确出处**（写作时不得含糊）：`runtime/internal/rules/rules.go` 全文件 89 行，含 package 注释、Category / Verdict 常量、Input / Decision 类型定义与 godoc；其中真正做判断的 `Decide` 函数为第 54–89 行，共 36 行。标题用 89（一个文件的完整体量，读者可自行核对），正文点明"真正做判断的只有 36 行"。不得写成 171 行——171 是 `rules.go` 与 `rules_test.go` 的合计。

**需要教的两个概念（用类比，不堆术语）**：
- **status vs verdict 正交**——"跑完了没"和"算不算过"是两件事。超时了是 status，超时该判 INFRA 还是 CODE 是 verdict。合并成一个枚举就再也拆不开。
- **Temporal**——类比为"能断点续跑的脚本引擎"：进程被杀掉重启后，靠重放历史回到断点继续。

**论证链（准确性要求，见下方"事实准确性红线"）**：
1. verdict 必须可复现、可回放——将来要做 MR 门禁，三个月后要能回答"为什么当时判 fail"。
2. `rules.Decide` 是纯函数、零 I/O，因此可以直接留在 workflow 代码中被重放重算。这是刻意设计，不是偷懒。
3. LLM 必须走 Activity（结果固化进 history 才重放安全）；但更重要的理由是 LLM 会挂、会超时、会限流，而已开始的任务必须能收敛到终态。
4. 分工结论：规则引擎裁决，LLM 解释。LLM 挂了，verdict 照出。

**落地细节**：
- 优先级链条：`CANCELED → 基础设施故障 → 客户端失败 → 签名命中 → TIMEOUT → 用例失败 → 退出码`。
- 精妙处：签名优先于 TIMEOUT 与用例计数。命中 `cpu_fallback` 说明模型没跑上 DSP（MODEL 类），不是代码问题（CODE 类）——信息量大的证据优先。
- LLM 的实际位置：`analyze_bridge`，调用时固定空工具集，输出必须过 JSON Schema，不过则把校验错误附回 prompt 重试上限 3 次，仍不过返回 502，Runtime 降级回规则引擎。

**收尾金句**：让 LLM 解释，不让 LLM 裁决。

**引用路径**：`runtime/internal/rules/rules.go`、`runtime/internal/workflow/devicetest.go`、`hermes/analyze_bridge/`

### 决定三：先写一个"注定被扔掉"的命令行工具

**钩子**：明知最终要做成 Windows 服务，为什么先花时间做个 CLI？

**论证链**：
1. Windows + USB + ADB 是全链路不确定性最高的一段（驱动、序列号、权限、adb server 冲突、PowerShell 编码）。
2. 而这些坑跟 Temporal、回调、幂等键毫无关系。
3. 若先写服务壳，每调一个 ADB 问题都要穿过五层抽象。
4. 转折：它并没有被扔掉。`executor` 被服务模式原样复用，接缝只是一个 `OnTransition` 钩子——CLI 不关心状态迁移通知谁，服务模式把它接到事件上报链上。

**落地细节**：
- 退出码 0/2/3/1，其中 2（测试没过）与 1（流水线自己坏了）刻意分开——这正是决定二中 status/verdict 正交在命令行层的投影，前后呼应。
- `--serial` 必填，错误信息直接写着"禁止无 -s 的 adb 操作"。
- 超时 kill 但仍然收集——超时往往正是最需要日志的时候。
- 私有 adb 端口 5137，永不碰系统的 5037。

**收尾金句**：先攻不确定性最高的那一段，用最薄的壳。

**引用路径**：`agent/cmd/agent-cli/main.go`、`agent/internal/executor/executor.go`

### 收束：这些决定值不值

三个真实踩坑印证：

| 踩坑 | 印证 |
|---|---|
| GitLab 13.8 版本号强制 `X.Y.Z`，版本号不变时新构建被 400 already-exists 静默 skip | 契约优先——唯一性必须编进文件名 |
| 固件报 SoC 代号 `trinket`，调度约束写型号 `QCM6125`，派单成功但预检失败 | agent-cli 先行——此坑在 CLI 阶段即暴露 |
| Docker 默认网段撞上内网真实设备 | 确定性优先于便利 |

**坦白一个已知缺口**（一句话带过）：`rules.Decide` 目前没有版本号，将来修改规则会破坏历史 workflow 的重放确定性；这是已识别、已排期的整改项（`docs/device-test-sequence.md` 差距清单第 7 项）。自曝一个清醒识别的缺口，比假装没有更能证明设计是清醒的。

**落点**：Phase 1 DoD 实测数据——push 一次代码后全自动跑完三个变体，全程无人工干预、零重复执行。

## 事实准确性红线

内部分享，讲错会被同事当场抓住。以下三点必须按此表述：

1. **不得写成"LLM 会破坏 Temporal 重放所以不能用"。** 这是错的：Activity 内调用 LLM 是重放安全的，结果固化在 history 中。真实理由是"verdict 必须可审计可复现"+"LLM 不可用时任务必须能收敛"。
2. **`rules.Decide` 留在 workflow 内是刻意设计**，因其为纯函数、零 I/O，不是因为图省事。
3. **"让 LLM 临场生成 adb 命令"是作为对比虚构的反面做法**，写作"最直觉的做法"，不得写成"有人提过"——无证据不虚构他人观点。
4. **规则引擎是 89 行，不是 171 行。** 171 是 `rules.go`(89) 与 `rules_test.go`(82) 的合计，属 LOC 统计口径错误。
5. **不得写"SNPE 1.68 与 2.21 的环境变量不同"**——二者 env 完全一致。真实差异在后端框架之间（SNPE 需 `ADSP_LIBRARY_PATH`，RKNN/TFLite 不需要）与 OS 之间（Android SNPE 的 `ADSP_LIBRARY_PATH` 含系统路径，Linux SNPE 不含），详见决定一的差异表。

**这两条红线的来历值得记下**：spec 第一版把规则引擎写成 171 行、把变体差异写成"SNPE 版本间 env 不同"，两处都是凭印象下笔，均由"验收标准最后一条：所有引用的代码事实必须回仓库逐一核对"当场证伪。写作阶段务必执行同一动作——凡出现具体数字、路径、字段名、日志文本，一律回仓库核对，不得凭本 spec 的转述二次传抄。

## 风格约定

**语言与术语**
- 中文写作。Temporal / workflow / verdict / Manifest 等术语首次出现时给一句白话解释，之后直接使用。
- 不翻译 status / verdict——二者的区分是全文核心，中译（"状态"/"判定"）反而糊。

**代码片段**：全文不超过 5 段，每段不超过 10 行。读者能读 Go，但博客不是代码走读。已选五段：
1. `manifest.yaml` 节选（`deploy.env` + `test.success`）——决定一
2. `adb.go` 模板函数签名 3 行，展示"没有 Exec(cmd)"——决定一
3. `rules.Decide` 优先级判断，截取 4 个分支——决定二
4. 退出码 switch——决定三
5. `OnTransition` 钩子的注入对比（CLI vs 服务）——决定三

- 全景横向流程图：5 个方框（CI → Trigger → Workflow → Agent → 开发板），回流线到飞书
- 规则引擎优先级链条：竖向决策流，7 个判断点

**可写真名**：`algo-super-sdk`、QCM6125、SNPE 1.68/2.21、GitLab 13.8、飞书、Temporal、MinIO
**不写**：内网域名、凭据配置项名、具体 IP 网段（"172.22 撞设备"改写为"Docker 默认网段撞上内网设备"）
